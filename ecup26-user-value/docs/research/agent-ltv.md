## 1. TL;DR

LTV modeling is per-scenario: feature engineering, objective design, and tuning
differ across business contexts, and pipelines are expensive to transfer. Authors
propose **AgentLTV**, a framework that treats each candidate solution as an
{executable pipeline program} generated by LLM-driven agents.

Two coordinated stages:
- **MCTS stage** — Polynomial UCT explores a broad space of modeling choices
  under a fixed budget; Pareto-aware multi-metric value function (not single metric).
- **EA stage** — island-based evolution with crossover / mutation / migration
  refines the best MCTS program.

Online bucket-level analysis reports improved ranking consistency and value
calibration, especially for high-value and negative-LTV segments.

## 2. What is genuinely new

- **Pipeline-as-program**: the search space is "executable code", not
  hyperparameter tuples. LLM agents *write, run, repair* the code.
- **Pareto-aware value function** during MCTS: balances ranking and error metrics
  rather than picking one scalar (RMSLE alone is too narrow).
- **Two-stage search**: MCTS for *breadth* (new data patterns), EA for *stable
  refinement*. Practitioner takeaway is explicit and useful.

## 3. Applicability to E-CUP T3 (user-value, RMSLE)

Our task: predict **sum GMV over 30 days** for 250k users from daily aggregate
history; metric RMSLE with log1p, `max(0, pred)`; submission `user_id,predict`.

### 3.1 Critical compliance caveat (must not be glossed over)

AgentLTV's inference path is **LLM agents running inference via local code
generation + execution**. Implementing it directly would mean:
- Calling an LLM (proprietary or open-weight) inside the submission pipeline.
- Maintaining an external LLM stack alongside our HF / sklearn / BTYD stack.
- Likely violating **R7** spirit ("single HF transformers pipeline") and
  potentially R4 (LLM inference is much heavier than BTYD).

So even where applicable, the *implementation* is not on the table. The *ideas*
are.

## 4. Concrete things to take into T3 backlog

1. **Bucket-level diagnostics for T3.6.12 ablation output.** Add a small
   helper that, given predictions and ground truth, splits users into GMV
   deciles and reports per-decile RMSLE + Spearman. Cost: ~30 LOC, ~0.5h.
   This catches calibration drift that the global RMSLE hides.
2. **Cite, don't copy**: if anyone proposes LLM-driven AutoML on this project,
   redirect to this note and to the **R7 caveat in §3.1**. We are not
   implementing it; we are taking the diagnostics idea only.
3. **No code change** to `run.py` from this paper.

## 5. What we explicitly reject

- LLM agents in the submission pipeline (R7 spirit, R4 likely).
- MCTS / EA outer loops — they require an LLM driver.
- Pipeline-as-code generation — orthogonal to our competition scope.
